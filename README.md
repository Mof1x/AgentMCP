# 🤖 Персональный Инструментальный AI-Агент (MCP + Telegram + SQLite)

Интеллектуальный агент для управления расписанием, повседневными делами и напоминаниями для обычной жизни человека с поддержкой уровней важности и фоновыми пуш-уведомлениями.

В проекте **не используется RAG**. Агент динамически исследует базу данных, выполняет цепочки инструментов (**Tool Chaining**) и взаимодействует с хранилищем через официальный стандарт **Model Context Protocol (MCP)**.

---

## 🏗️ Архитектура системы

```
[ Telegram Client (User) ]
            │ (User Message)
            ▼
   [ Telegram Bot ]  (aiogram 3.x)
            │
            ▼
[ Agent Core / Orchestrator ] ◄────► [ LLM (Function Calling) ]
            │ (JSON-RPC over stdio)     (GPT-4o / DeepSeek / etc.)
            ▼
    [ MCP Server ]   (MCPServer / stdio transport)
            │
            ▼
   [ SQLite Database ]
   (events, reminders, categories)
            ▲
            │ (проверка раз в 30 сек)
[ Background Reminder Worker ] ────► [ Отправка пуша в Telegram ]
```

---

## 🛠️ Набор инструментов MCP (Tools)

1. **`get_current_datetime`**: Возвращает текущее время, дату и день недели. Позволяет разрешать относительные фразы («завтра», «в эту пятницу», «через 2 часа»).
2. **`get_db_schema`**: Возвращает структуру таблиц, типы полей, внешние ключи и уровни важности. Модель исследует БД «на лету» без зашитой схемы в промпте.
3. **`check_time_conflict`**: Проверяет наложение нового дела на уже запланированные. Анализирует уровни важности пересекающихся дел.
4. **`execute_read_query`**: Безопасный `SELECT`. Блокирует деструктивные ключевые слова (`INSERT`, `UPDATE`, `DELETE`, `DROP`).
5. **`execute_write_query`**: Выполняет `INSERT`, `UPDATE`, `DELETE` для создания/переноса событий и установки напоминаний.
6. **`find_free_slots`**: Находит свободные интервалы для дела заданной длительности в расписании пользователя.
7. **`get_day_summary`**: Рассчитывает загруженность выбранного периода и находит самый длинный свободный промежуток.
8. **`create_recurring_events`**: Создаёт конечную серию событий с проверкой конфликтов всех дат.
9. **`reschedule_event`**: Переносит событие вместе с неотправленными напоминаниями.
10. **`export_schedule`**: Формирует содержимое календаря в формате ICS.
11. **`get_overdue_events`**: Показывает прошедшие события, выполнение которых ещё не отмечено.
12. **`create_event_with_reminders`**: Создаёт событие со всеми напоминаниями в одной транзакции, проверяя конфликты и сохраняя квитанцию операции.

### 🎯 Уровни важности (Priority):
* 🔴 **4 — CRITICAL**: Врачи, авиабилеты, поезда, экзамены (нельзя двигать!).
* 🟡 **3 — HIGH**: Важные рабочие созвоны, встречи, дедлайны.
* 🟢 **2 — MEDIUM**: Обычные дела, тренировки, хобби, уборка.
* ⚪ **1 — LOW**: Бытовые мелочи, покупка продуктов, дела без дедлайна.

## 🚀 Быстрый старт

### 1. Установка зависимостей
Убедитесь, что активировано виртуальное окружение, и выполните:
```bash
pip install -r requirements.txt
```

### 2. Настройка конфигурации (.env)
Скопируйте пример файла конфигурации:
```bash
cp .env.example .env
```
Откройте файл `.env` и укажите:
* `TELEGRAM_BOT_TOKEN` — токен от [@BotFather](https://t.me/BotFather).
* `OPENAI_API_KEY` — ключ API к LLM (OpenAI, DeepSeek, OpenRouter и др.).
* (Опционально) `OPENAI_BASE_URL` — базовый URL стороннего провайдера (например, `https://api.deepseek.com/v1`).
* `LLM_MODEL` — модель (например, `gpt-4o-mini`, `gpt-4o`, `deepseek-chat`).

### 3. Заполнение базы данных тестовыми данными
```bash
python database/seed_data.py
```

### 4. Запуск автоматических тестов
Все тесты, включая MCP stdio, атомарное сохранение и резервные ответы при сбоях:
```bash
python -m unittest discover -s tests -v
```

### 5. Запуск в консоли (без Telegram)
Для быстрой отладки логики и просмотра работы Tool Chaining в терминале:
```bash
python test_agent_cli.py
```

### 6. Запуск Telegram-бота
```bash
python main.py
```

## 🔄 Пример цепочки инструментов (Tool Chaining)

**Запрос пользователя:**
> *«Запиши меня завтра к окулисту на 16:00, это займет примерно час. Дело важное, напомни за 3 часа и за 30 минут.»*

**Логика работы агента:**
1. `get_current_datetime()` $\rightarrow$ Определение завтрашней даты.
2. `get_db_schema()` $\rightarrow$ Получение структуры колонок и связей.
3. Подготовка параметров события и напоминаний; конфликты проверяются внутри операции создания.
4. `create_event_with_reminders(...)` $\rightarrow$ Атомарное создание события и двух напоминаний.
5. Проверка результата сохранения: событие, напоминания (в 13:00 и 15:30) и квитанция записываются вместе.
6. Формирование финального ответа пользователю с отчетом.
7. В назначенное время фоновый воркер `reminders_worker.py` пришлет пуш-сообщение в Telegram.


## Поиск свободного времени

Добавлен MCP-инструмент `find_free_slots`, который находит свободные
промежутки в расписании пользователя для дела заданной длительности.

Пример запроса:
«Найди завтра свободный час для тренировки между 10:00 и 20:00».

Параметры инструмента:
- `date` — дата поиска в формате YYYY-MM-DD;
- `chat_id` — идентификатор чата пользователя;
- `duration_minutes` — длительность дела в минутах;
- `day_start` и `day_end` — границы поиска в формате HH:MM.

Инструмент учитывает только запланированные события указанного
пользователя, включая события на весь день. Пересекающиеся дела
обрабатываются как общее занятое время.

Результат — свободные интервалы не короче указанной длительности.
Поиск не создаёт событие автоматически: пользователь выбирает время,
после чего агент повторно проверяет конфликты перед сохранением.

Добавлены 4 модульных теста и проверка регистрации инструмента
на MCP-сервере. Все 16 тестов проекта проходят.


## Статистика загруженности дня

Добавлен MCP-инструмент `get_day_summary`.

Пример запроса:
«Насколько у меня загружен завтрашний день с 09:00 до 21:00?»

Параметры:
- `date` — дата в формате YYYY-MM-DD;
- `chat_id` — идентификатор чата пользователя;
- `day_start` и `day_end` — границы анализируемого периода в формате HH:MM.

Инструмент возвращает:
- количество запланированных событий, пересекающих выбранный период;
- занятое и свободное время в минутах;
- процент загруженности периода;
- самый длинный свободный промежуток.

Пересекающиеся события не увеличивают занятое время повторно.
События за границами периода учитываются только в пересекающейся части.
Отменённые и выполненные события, а также дела других пользователей
не учитываются. Поддерживаются события на весь день.

Добавлены 5 модульных тестов статистики и проверка регистрации
инструмента на MCP-сервере. Все 40 тестов проекта проходят.


## Дополнительные возможности

### Повторяющиеся события

Пример: «Добавь четыре тренировки по воскресеньям с 1 ноября
2026 года в 10:00, длительность — час».

Инструмент create_recurring_events создаёт от 1 до 52 событий
с одинаковым интервалом в днях. Первое событие входит в количество.
Если хотя бы одна дата конфликтует с расписанием пользователя,
вся серия остаётся несохранённой.

Каждый повтор хранится как отдельное событие.
Напоминания добавляются отдельно. Ежемесячные повторы не поддерживаются.

### Перенос вместе с напоминаниями

Пример: «Перенеси встречу с 15:00 на 17:00».

Инструмент reschedule_event сохраняет длительность события
и сдвигает неотправленные напоминания на ту же разницу времени.
Отправленные напоминания не изменяются.
При конфликте событие и напоминания остаются без изменений.
Перенос событий на весь день этим инструментом не поддерживается.

### Экспорт календаря

Команда Telegram:
/export 2026-11-01 2026-11-07

Бот отправляет файл .ics с запланированными событиями пользователя.
Обе даты включаются в период. Максимальный период — 366 дней.
События, пересекающие границу периода, экспортируются целиком.
Напоминания не экспортируются.

Время встреч трактуется как местное время календаря,
в который импортируется файл.

MCP-инструмент export_schedule формирует содержимое календаря.
Отправку документа выполняет обработчик команды /export.

### Поиск времени с перерывами

Пример: «Найди свободный час с 09:00 до 21:00,
оставив по 15 минут между делами».

Параметр buffer_minutes инструмента find_free_slots задаёт
минимальный перерыв между новым делом и соседними событиями.
По умолчанию он равен нулю. Поиск не изменяет расписание.

### Незавершённые прошлые дела

Пример: «Покажи дела за последние семь дней,
которые ещё не отмечены выполненными».

Инструмент get_overdue_events показывает события со статусом planned,
время окончания которых уже наступило.
Это означает отсутствие отметки о выполнении в боте,
а не подтверждение того, что пользователь не выполнил дело.

Результаты сортируются по важности, затем по времени окончания.
Поддерживаются фильтр по периоду и ограничение количества результатов.
Статусы событий автоматически не меняются.
## Атомарное создание и ответы при сбоях

Для создания одиночного события агент использует `create_event_with_reminders`.
В аргументах передаются название, начало, необязательное окончание, описание,
категория, важность, признак события на весь день и список `reminders`:
каждое напоминание содержит `remind_at` и необязательный `custom_message`.
Даты имеют формат `YYYY-MM-DD HH:MM:SS`.

Событие, все напоминания и запись в `creation_receipts` сохраняются одной
транзакцией. Ошибка при добавлении любого напоминания откатывает всю операцию.
Таблица квитанций автоматически добавляется при обычном запуске `main.py`
через `init_db()`; существующие события сохраняются.

Оркестратор подставляет настоящий `chat_id` и идентификатор операции.
Эти поля не показываются модели в схеме нового инструмента.
Повтор одинакового вызова в пределах одного обрабатываемого сообщения
использует тот же идентификатор и возвращает квитанцию без повторной записи.
Это не дедупликация новых сообщений Telegram и не гарантия для произвольного SQL.

При потере ответа инструмента приложение читает квитанцию через служебный
MCP-инструмент `get_creation_result` (он скрыт из списка инструментов модели).
Отсутствие квитанции трактуется как неизвестный результат, а не как доказательство
отката: исходная операция ещё могла выполняться. В этом случае обработка
останавливается без автоматического повтора записи.

При отказе модели, пустом ответе или исчерпании шагов резервный ответ формируется
обычным кодом из результатов текущего запроса. Дополнительного обращения к LLM
для объяснения ошибки нет. Подтверждённые операции перечисляются отдельно
от неудачных и операций с неизвестным результатом. Квитанция подтверждает факт
создания, а не текущее состояние события после последующих изменений.

Свободные SQL-запросы и остальные инструменты сохранены. Их подтверждённые
изменения также учитываются в резервном ответе, но отдельные SQL-вызовы
не становятся общей транзакцией. Повторяющиеся события с отдельно добавляемыми
напоминаниями не получают атомарность нового инструмента.

Проверка: `python -m unittest discover -s tests -v`.
Все тесты используют временные базы; основной тестовый модуль больше не очищает
рабочую базу. Тесты отказов API используют имитацию модели, а интеграционные
проверки запускают настоящий локальный MCP-сервер. Telegram и внешний API
при прогоне не вызываются. Консольный демонстрационный режим по-прежнему вызывает
`seed()` — его следует запускать с отдельным `DB_PATH`.
